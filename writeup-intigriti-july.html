0. What “done” means for this contest

The landing page sets the rules: solution in latest Chrome, not self-XSS, not MitM, and a flag of the form INTIGRITI{...}. The app itself says the important part out loud: “A protected report contains the flag.”

That line steers the whole investigation. If the flag lives inside a report that normal users should not be able to order, then spraying XSS into React text nodes is the wrong main bet. The productive question is: how do I get the server to build and return a report for a package I am not allowed to target?

1. Mental model of the app

Registry Observatory is a small Vite + React SPA at /challenge.html. It pretends to be a private package registry with a preflight workflow. In plain terms, a logged-in user can ask: “Does this package exist, what is its latest version, and what are the release notes?” The answer comes back as a read-only publication report.

The product flow is linear:

  1. Register or log in. You get a private namespace (scope) and a CSRF token.
  2. Fill a JSON manifest that names a package triple: scope, name, version.
  3. Base64-encode that JSON into manifest_b64.
  4. Preview the manifest (schema and ownership checks).
  5. Sign it. The server returns a short-lived approval blob (id, hash, nonce, expiry, signature).
  6. Publish by replaying manifest_b64 plus the approval fields.
  7. Read the report: existence, version, compatibility text, release notes.

UI tabs matter for recon, not for the bug itself: Overview (workspace), Observatory archive (lore and hints), Manifest Studio (the happy-path form), and Publication history (every report you ordered).

2. Session, CSRF, and API surface

Unauthenticated recon already shows a thin, explicit API under /api/*. Nothing fancy: register, login, me, packages, manifests, publications, health. Session is a cookie named cy_session (HttpOnly, SameSite=Strict). Mutations need header x-csrf-token taken from GET /api/me.

That design is standard and solid for cookie sessions. CSRF is not the bug. Cookie flags are not the bug. The bug lives one layer deeper: how the server interprets the JSON inside manifest_b64.

3. Finding the crown jewel

The app does not hide the target package. The Observatory archive and component index name it directly.

  • Platform-maintained scope: core
  • Restricted component: security-notes (record CR-17, version 1.0.0)
  • Copy text: transfer into platform-maintained namespace; restricted maintenance component

Direct package detail is blocked. That is expected and useful: it proves the object exists and that a normal ACL rejects you.

Working hypothesis after recon: do not steal the package detail endpoint. Steal the preflight report pipeline, because that pipeline is the only place the app admits the flag lives.

4. What the client hard-codes (and why that is not security)

Reading the SPA JS shows the browser always builds a “safe” manifest shape: 

operation: "preflight"
visibility: "private"
package.scope: user.namespace   // UI field is read-only
package.name: from form
package.version: from form
metadata.description: from form

It pretty-prints that object as JSON, UTF-8 encodes it, then Base64-encodes the bytes into manifest_b64. Sign returns approval_id, manifest_sha256, nonce, expires_at, and signature. Publish resubmits those fields with the same manifest_b64.

Two lessons from the client:

  1. Client hard-codes are UX, not policy. If you can call the API with curl, you can send any base64 JSON that the server accepts. The read-only scope field is irrelevant.
  2. Approvals bind to bytes. The hash covers the exact decoded manifest bytes (or the exact manifest_b64 content after decode). You cannot sign package A and publish package B by swapping only the package fields after signing.

Side notes from package copy that nudged later thinking:

  • legacy-adapter release notes mention that historical ingestion keeps the initial package declaration, while report rendering uses reconstructed manifest data. That smells like more than one interpretation of the same document.
  • compat-sample says protected findings are not included in ordinary reports.

5. Negative tests that map the real boundary

With a real account, run the happy path first. Preflight your own hello-world. You get a normal report. Pipeline works.

Then break one assumption at a time. The table below is the map that actually led to the bug. Each row is a real request, not a guess.

ExperimentResultLesson
Preflight own hello-world Report ready, ordinary release notes End-to-end pipeline works
scope: "core" alone Preview / sign rejected Ownership is enforced somewhere
Own scope + name security-notes status: not_found Name alone does not cross scopes
Sign own package, publish core package bytes Publication approval invalid Signature binds full manifest bytes
Extra keys, __proto__, wrong operation or visibility Rejected Schema is strict on members and enums
Duplicate name keys inside one package object Last name used for report target Per-field parse is last-wins
Core package first, own package second Preview fails First top-level package object drives authz
Own package first, core package second Flag Last top-level package object drives report identity

Also ruled out while hunting:

  • Stored XSS via description: React renders report fields as text children, not HTML.
  • Approval field mix-and-match: hash and signature checks hold.
  • Cross-user publication IDOR: other users cannot read your publication id.
  • Unicode confusables for scope, path tricks on package URLs, basic prototype pollution on register/login/publish.

CSP allows 'unsafe-inline', so if an HTML sink existed, classic XSS would matter. In this app path, it did not. The flag was never in a reflected description field.

6. JSON on the wire: ordered text vs abstract maps

This is the first-principles piece. Skip it and the exploit looks like a magic string. Include it and the bug is obvious once you see the dual read.

In the abstract data model, a JSON object is a collection of name/value pairs. In the ECMA-404 text format, an object is a sequence of members between braces. The standard does not define what happens when the same name appears twice. Real parsers almost always keep the last value and drop earlier ones when they build a map.

That is fine if every later step uses the same map. It is not fine if:

  1. one check walks the raw text (or a multi-map) and takes the first member named package, and
  2. another step builds a normal object and takes the last member named package.

You then have two truths inside one document. Authz can pass for truth A while the report is built from truth B.

7. The bug: first package for authz, last for the report

On this service, the empirical model is simple:

  • First top-level "package" object: authorization. Scope must equal the caller’s namespace.
  • Last top-level "package" object: package identity for preflight and release notes.

Control experiment: reverse the order (core first, own second). Preview fails. That is the fingerprint of first-for-auth, last-for-action. If both steps used last-wins only, reverse order would still authorize you (own last) and then report on your own package. It does not. Order matters because the checks disagree.

Root cause in one sentence: the server never canonicalizes the decoded manifest to a single package object before applying both authorization and report generation, so duplicate keys create two package identities in one request.

Important detail: the first package name must be a package that exists in your namespace if you care about a clean “package exists” report path for your own identity, but the decisive part is the last object’s triple. In practice we used hello-world as the first package because it is a seeded starter package.

The signed hash still covers the full ambiguous bytes. That is why approval swap attacks fail, but dual-key polyglots succeed: you sign the polyglot once, and every step after sign still sees the same bytes. Authz and action still split those same bytes differently.

8. Full exploit path you can replay

Everything below is enough to reproduce from a clean browser or from curl. Screenshots use pinchtab (local Chrome control plane) on the live challenge.

  1. Open https://challenge-0726.intigriti.io/challenge.html and register or log in.
  2. GET /api/me with cookies. Read user.namespace and csrf_token.
  3. Build the dual-package JSON (section 8.1). First package uses your namespace. Second uses core / security-notes / 1.0.0.
  4. UTF-8 encode, standard Base64, call that string manifest_b64.
  5. POST /api/manifests/preview with Content-Type: application/json and header x-csrf-token.
  6. POST /api/manifests/sign with the same body. Keep the full approval object.
  7. POST /api/publications with manifest_b64 plus approval fields.
  8. GET /api/publications/{publication_id}. Flag is in report.release_notes.

8.1 Payload (raw JSON before Base64)

{
  "package": {
    "scope": "<YOUR_NAMESPACE>",
    "name": "hello-world",
    "version": "1.0.0"
  },
  "package": {
    "scope": "core",
    "name": "security-notes",
    "version": "1.0.0"
  },
  "metadata": {
    "description": "x",
    "visibility": "private"
  },
  "operation": "preflight"
}

Replace <YOUR_NAMESPACE> with the value from /api/me (example used here: hax44265-d098d1e1). Do not include the leading @ in the JSON scope field; the API uses the bare namespace string.

9. Why this is not “only last-wins JSON”

Last-wins alone is not a vulnerability if the whole pipeline uses one object. The vulnerability is the split brain:

  • One interpretation answers: “Is this caller allowed to request a preflight?”
  • Another interpretation answers: “Which package’s protected notes do we emit?”

Related negatives that guided the search before the dual-package hit:

  • Duplicate scope keys inside one package object were rejected even when identical. That path is stricter than top-level duplicate package members.
  • Sending two operation values (preflight then transfer) could get past sign and still fail at publish. That showed multi-key weirdness without yet giving the flag.
  • React text rendering made classic stored XSS in description a dead end. The crown jewel was always the core report.

Contest marketing frames the series as XSS CTFs. For this month, the impact still ends on the protected report. The exploitable bug class is server-side authorization failure via JSON parse disagreement, not a browser script sink.

10. Impact, fixes, and submission package

10.1 Impact

  • Confidentiality: any authenticated user can retrieve the platform-protected preflight report for @core/security-notes, including the challenge flag and any secrets that report would contain in a real registry.
  • Trust model: a signed approval no longer means “this exact package identity was authorized” if package identity is ambiguous under the parser.
  • No victim interaction: no MitM, no self-XSS, no click from another user. The attacker orders the report in their own session.

10.2 Fix recommendations

  1. Reject duplicate keys at parse time (strict JSON parser or schema validator), or parse once into a single map and never re-walk raw text for a second package identity.
  2. One package object only in the schema. Assert package.scope === session.namespace on that object after canonicalization.
  3. Bind the canonical package triple (scope, name, version) into the signature material after validation. Hashing raw ambiguous bytes protects integrity of those bytes, not semantic uniqueness of package identity.
  4. Re-check ACL on the resolved package identity immediately before reading protected release notes, even if preview already passed.

10.3 Timeline of reasoning (how we actually got there)

  1. Read JS: no app dangerouslySetInnerHTML; flag narrative points at protected report.
  2. Account + happy path preflight of own packages.
  3. Direct core scope blocked; approval swaps blocked; extra keys blocked.
  4. Observatory CR-17 and component index name the target package and version.
  5. Duplicate-key probes: field-level last-wins; multi-key oddities around operations.
  6. Dual top-level package objects: first-auth / last-action returns the flag.
