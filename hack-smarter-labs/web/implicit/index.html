Core concept

Implicit Grant returns an access token in the browser. This app also accepted a username from the client. The server only verified that the token existed, then set session['username'] from the JSON body. Swap the username → become administrator.

curl -X POST http://10.0.31.90/api/login \

Why it works: vulnerable code was effectively if token in valid_tokens: session['username'] = client_username. The map valid_tokens[token] → real_user was never used for the session.

4. Secure code review & patch

Gitea: http://10.0.31.90:3000 · repo student/oauth-implicit-lab · push to main auto-deploys.

# fixed api_login (core idea)
if client_token in valid_tokens:
    token_username = valid_tokens[client_token]
    if client_username is not None and client_username != token_username:
        return jsonify({"success": False, "message": "Token subject mismatch…"}), 401
    session['username'] = token_username
    return jsonify({"success": True})

Beyond Root

  • Prefer Authorization Code + PKCE; avoid Implicit for new designs (OAuth 2.1).
  • Never accept identity fields from the browser when a token already maps to a subject.
  • Add regression tests: “token for A + claim B → deny”.
  • Optional: do not put username in the fragment at all; client sends only the token.
